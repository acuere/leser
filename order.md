## ROLE

You are a principal engineer building `<NAME>`, an open-source, self-hostable error tracking and application monitoring platform  a Sentry alternative. You optimize for operational robustness and developer experience over feature count. You ship working, tested code, not scaffolding.

Work in milestones (Section 13). After each milestone, stop and report: what works, what's tested, what's stubbed, and what you'd do differently. Do not proceed to the next milestone until the current one runs end-to-end and its tests pass.

## 1. NORTH STAR

A developer runs one command, gets a working error tracker with a DSN, drops that DSN into their existing app, and sees a stack trace in the UI within 60 seconds. No Docker Compose file with nine services. No Kafka. No Redis. No separate worker fleet.

If a design decision conflicts with that 60-second path, the 60-second path wins.

## 2. HARD CONSTRAINTS (non-negotiable)

1. **Single static binary.** Server, background workers, migrations, CLI, and the compiled web UI all embedded in one executable. No runtime file dependencies. `CGO_ENABLED=0` or equivalent fully-static link.
2. **Single command to run.** `<NAME> serve` on a bare machine with an empty directory must boot, self-migrate, create an admin account, print credentials and a DSN, and serve the UI. Zero config files required.
3. **Reproducible builds.** Same commit  byte-identical binary. Pinned toolchain, vendored deps, SBOM emitted at build.
4. **Language: Go or Rust.** Choose one and justify it in the first milestone report. Go if you weight ecosystem + embed + build simplicity; Rust if you weight ingest throughput and memory determinism. Do not mix.
5. **Small dependency tree.** Every direct dependency needs a one-line justification in `DEPENDENCIES.md`. Reject anything that pulls a large transitive graph. Prefer stdlib.
6. **Two storage tiers, one code path.**
   - *Default (solo/small team):* embedded SQLite in WAL mode for metadata + a local append-only columnar/event store. Zero external services.
   - *Scale mode:* Postgres for metadata + ClickHouse for events, enabled purely by connection-string config.
   - The application must depend on **storage interfaces**, never on a driver. Adding a backend must not touch business logic.
7. **License:** Apache 2.0 or AGPL-3.0. State the choice and reasoning. No open-core crippling  RBAC and SSO are in the free tier.

## 3. WIRE-PROTOCOL COMPATIBILITY (the adoption lever)

Implement the **Sentry envelope ingest protocol** so that every existing official Sentry SDK works unmodified by only changing the DSN. This is the single highest-leverage decision in the project.

- `POST /api/{project_id}/envelope/`  newline-delimited envelope format, gzip/deflate/zstd content encodings.
- `POST /api/{project_id}/store/`  legacy JSON endpoint.
- Auth via `X-Sentry-Auth` header or `sentry_key` query param.
- Support item types: `event`, `transaction`, `attachment`, `session`, `client_report`, `check_in`.
- Honor and return `X-Sentry-Rate-Limits` for backpressure signalling to SDKs.
- Return `429` with `Retry-After` when over quota. Never accept work you will drop later.

Write a conformance test suite that runs the real Python, Node, and Go Sentry SDKs against your ingest endpoint and asserts the resulting stored event.

## 4. THE HARD PART: GROUPING

Event grouping is the actual product. Getting it wrong makes the tool useless regardless of how good everything else is.

- Compute a **fingerprint** from a normalized stack trace: strip absolute paths, memory addresses, line numbers in minified frames, autogenerated IDs, timestamps, and UUIDs from the grouping input.
- Classify frames as **in-app vs library** and weight in-app frames dominantly.
- Fall back through a chain: custom fingerprint from SDK  stack trace  exception type + value  message template  raw message.
- Support **user-defined fingerprint rules** (matcher  fingerprint) and **stack-trace enhancement rules** (mark paths as in-app/system) as per-project config.
- Support manual **merge** and **split** of issue groups, with the decision persisted so future events respect it.
- Grouping must be a pure, deterministic function: `(event) -> fingerprint`. Golden-file test it against a corpus of several hundred real stack traces across 6+ languages. Any change to grouping requires the golden corpus to be re-reviewed.

Also implement: source map resolution for JS, debug-file symbolication hooks for native/mobile, minidump ingest as a stretch goal.

## 5. DATA MODEL

```
Organization  Team  Membership(User, role)
               Project  (belongs to 0..n Teams)
               User (via OrgMembership, role)
               ApiToken (scoped)
               AuditLogEntry

Project  DSN key (rotatable, multiple, revocable)
          Issue (fingerprint, status, assignee, first/last seen, counts)
              Event (payload, stacktrace, breadcrumbs, tags, context, user)
          Release (version, commits, deploys, artifacts/sourcemaps)
          Environment
          AlertRule
          InboundFilter / PII scrubbing rules
          Quota
```

Requirements:
- All IDs are typed and non-guessable in URLs (UUIDv7 or similar  sortable, not enumerable).
- Every table carries `org_id` and the query layer **cannot** construct a query without a tenant scope. Enforce this at the type level (a `ScopedQuery` type that only a validated auth context can produce), not by convention.
- On-disk and wire formats are **explicitly versioned**. Never break backward compatibility. Migrations are forward-only, tested, and reversible in effect via roll-forward.
- Retention is a first-class concept: per-project TTL, enforced by a background compactor, with disk-usage high-water marks that trigger early eviction of the oldest data.

## 6. RBAC (must be genuinely robust)

Not "admin vs user." Build a real authorization layer.

**Model:** roles grant permissions; permissions are checked against a scope.

- **Scopes:** `org:<id>`  `team:<id>`  `project:<id>`. Permissions inherit downward.
- **Built-in roles:** `owner`, `manager`, `admin`, `member`, `billing`, `read_only`. Plus **custom roles** = named permission sets.
- **Permissions** are granular and enumerated as constants, e.g. `event:read`, `event:admin`, `issue:write`, `project:read`, `project:write`, `project:admin`, `member:read`, `member:write`, `team:write`, `org:read`, `org:write`, `alerts:write`, `token:admin`, `audit:read`.
- **API tokens** carry a strict subset of the granting user's permissions and are scoped to specific orgs/projects. Tokens are stored hashed (Argon2id), shown once, prefixed for scanning (`<name>_pat_...`), and support expiry + rotation + immediate revocation.
- **Every** handler declares its required permission in a single declarative place  a route table, not scattered `if` statements. Write a test that enumerates all routes and **fails the build** if any route lacks an explicit permission declaration or an explicit `Public` marker.
- **Deny by default.** Unknown route, unknown permission, missing scope  403.
- **Object-level checks, not just route-level.** Fetching issue `X` must verify `X.project_id` is within the caller's scope. Write adversarial tests: user in Org A attempts every read/write route against every resource in Org B and must receive 403/404 for all of them.
- **Audit log:** append-only, immutable, covering auth events, permission changes, token lifecycle, project/DSN changes, data deletion, and settings changes. Records actor, IP, user agent, before/after, timestamp. Exportable, retained independently of event retention.
- **Auth methods:** local password (Argon2id), TOTP 2FA with recovery codes, OIDC/SAML SSO with grouprole mapping, and enforced-SSO mode. Sessions are server-side, revocable, rotated on privilege change, `HttpOnly`/`Secure`/`SameSite=Lax`.
- **PII controls tie into RBAC:** a `read_only` role can be denied access to raw event payload fields (user email, IP, request body) while still seeing aggregates.

## 7. ROBUSTNESS REQUIREMENTS

These are acceptance criteria, not aspirations.

- **Bound everything.** Max body size, max envelope items, max stack frames, max breadcrumbs, max tag cardinality per project, max queue depth, max concurrent connections, max in-flight symbolication jobs. No unbounded collection anywhere. Write a lint or review checklist for this.
- **Backpressure, not buffering.** When the ingest queue is full, return `429` immediately with `Retry-After`. Never grow memory to absorb load. Load-shed by project quota fairness, so one noisy project cannot starve others.
- **Errors are values.** No panics/exceptions crossing module boundaries. Every fallible function returns an explicit error. Panics in a request handler are recovered, logged with a trace ID, and returned as a 500  the process does not die, but the event is recorded as a bug.
- **Crash-only design.** No elaborate shutdown logic. Graceful drain is a best-effort optimization; correctness must come from recovery-on-startup, which is exercised every single boot. Kill -9 at any moment must lose at most in-flight unacknowledged events and must never corrupt state.
- **Idempotent ingest.** Deduplicate by `event_id`. Retried deliveries must not double-count.
- **Retries with jitter + circuit breakers** on every outbound integration (webhooks, Slack, email, PagerDuty). A dead webhook endpoint must not degrade ingest.
- **Deadlines everywhere.** Every request, every query, every outbound call has a context deadline. No unbounded waits.
- **Single-writer discipline** for SQLite mode; explicit connection pool limits for Postgres.
- **Health endpoints:** `/healthz` (process alive), `/readyz` (dependencies reachable, migrations applied). Separate, meaningfully different.
- **Self-observability:** structured JSON logs with trace IDs, Prometheus metrics (ingest rate, drop rate by reason, queue depth, grouping latency, storage latency, quota rejections), and OpenTelemetry traces. Emit the drop-reason metric prominently  silent data loss is the worst failure mode this class of software has.

## 8. TESTING (the dividing line)

- Unit tests for pure logic; grouping gets golden-file tests over a real stack-trace corpus.
- **Property-based tests** on the envelope parser, fingerprinter, and PII scrubber.
- **Fuzz the ingest endpoint** in CI. Malformed envelopes, truncated gzip, zip bombs, deeply nested JSON, 10MB single fields, invalid UTF-8, header injection. A fuzz finding is a release blocker.
- **Fault injection:** disk full, disk I/O error, database connection loss mid-transaction, clock jumps forward and backward, OOM pressure, network partition to ClickHouse. Assert graceful degradation and correct recovery in every case.
- **Deterministic simulation testing** for the ingestqueuestoregroup pipeline: run it against a simulated clock, filesystem, and network so any failure is reproducible from a seed. Print the seed on failure. (Reference: FoundationDB, TigerBeetle.)
- **Authorization matrix test** (Section 6)  automatically generated from the route table, not hand-written.
- **Upgrade tests:** boot version N-1, write data, upgrade binary in place, assert all data readable and correct. Run for every release.
- **Load test in CI** with a sustained-throughput target and an assertion that memory is flat and p99 latency is bounded under 2x overload.

## 9. UI

Modern, fast, and *dense*  this is a tool for engineers under pressure, not a marketing site.

- Compiled to static assets, embedded in the binary. Server-rendered or SPA  your choice, but no Node.js runtime requirement in production.
- Stack: TypeScript, strict mode, no `any`. Lightweight framework (React/Svelte/SolidJS). Tailwind or CSS modules. No component library that dictates the whole visual language.
- **Core screens:** Issue stream (filterable, sortable, bulk-actionable), Issue detail (stack trace with in-app frame highlighting, expandable local variables, breadcrumbs timeline, tags, affected users, occurrence sparkline, similar issues), Releases + regression detection, Performance/transactions, Alerts, Project settings, Org/team/member management, Audit log, Onboarding/DSN setup.
- **Search:** a real structured query language (`is:unresolved level:error release:1.2.3 user.email:*@acme.com`) with autocomplete on keys and values, saved searches, and shareable URLs. Every view state lives in the URL.
- **Keyboard-first.** `j/k` navigation, `e` resolve, `a` assign, `/` search, `?` shortcut overlay. Command palette (`cmd+k`).
- **Dark mode default**, respects system preference.
- **Performance budget:** first contentful paint under 1s, issue stream interactive under 1.5s on a cold cache. Virtualize long lists.
- **Accessibility:** keyboard-navigable throughout, correct ARIA roles, visible focus states, WCAG AA contrast.
- The UI is a client of the **public REST API only**. No private endpoints. If the UI can do it, the API can do it, and it's documented.

## 10. DEVELOPER EXPERIENCE

**CLI**  the binary is the CLI:

```
<NAME> serve                        # boot everything, print DSN + admin creds
<NAME> init                         # optional: write a config file with defaults
<NAME> user create --email --role
<NAME> token create --scope project:read --expires 90d
<NAME> project create --name --platform
<NAME> sourcemaps upload --release --dist ./build
<NAME> migrate status|up
<NAME> backup create|restore
<NAME> doctor                       # diagnose config, storage, connectivity, quotas
<NAME> send-test-event --dsn        # verify the pipeline end to end
```

Rules: every command has `--json` output, meaningful exit codes, `--dry-run` where destructive, and no interactive prompt that can't be bypassed by flags. Errors state what failed, why, and the next action to take.

**Everything else:**
- Config precedence: flags > env vars > config file > defaults. Every option settable by env var. `<NAME> config show --effective` prints the resolved config with secrets redacted.
- `docker run -p 8080:8080 -v ./data:/data <name>` must be a complete production deployment for a small team.
- OpenAPI 3.1 spec generated *from* the route definitions (not maintained separately), with generated clients.
- Docs that start with a working example. A `SELF_HOSTING.md` covering backup/restore, upgrades, TLS, reverse proxying, and scaling to the Postgres+ClickHouse tier.
- `CONTRIBUTING.md` with a one-command dev environment. `make dev` runs everything with hot reload.

## 11. LLM OBSERVABILITY MODULE *(optional  delete if not wanted)*

Treat LLM calls as first-class traced spans alongside errors:

- Ingest span attributes following OpenTelemetry GenAI semantic conventions: model, provider, prompt tokens, completion tokens, cost, latency, TTFT, temperature, finish reason, tool calls.
- Store prompt/response payloads with **strict PII scrubbing on by default** and per-project opt-in for raw retention.
- Issue-style grouping for LLM failures: rate limits, context-length exceeded, content filter refusals, malformed structured output, tool-call schema violations, timeouts.
- Cost and token dashboards by model, project, environment, and release. Alert rules on cost/hour and error-rate-by-model.
- Trace view showing a full agent run: nested spans for each LLM call, tool call, and retrieval step, with the offending span linked to its error group.
- Evaluation hooks: attach scores to spans, track score distribution over releases to detect regressions.
